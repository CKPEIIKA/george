# Publishing George

The release publisher is generated by
`node tools/prepare-publication.mjs --update --fast-forward`. It prepares
the committed source in `publish/main` and its `web/` tree plus the
deployment workflow in `publish/gh-pages`. The static files stay at the
site branch's root; `build/publication/plan.json` records the reviewed refs.

Run `bash build/publication/publish.sh` from the repository. The script
checks the prepared refs, pushes both atomically without forcing, then
waits for that site commit's Pages workflow. It verifies the served
HTML, UI sources, the isolation worker, all five runtime manifests and assets, and the
corresponding source archive against the commit.
Failure returns a nonzero exit status with the workflow URL. Verification
uses Node and Git; it does not require GitHub CLI or an API token for this
public repository. An existing `GH_TOKEN` or `GITHUB_TOKEN` may be used for
read-only status requests. Optional SSH-key loading remains supported.

## Automatic deployment

`.github/workflows/pages.yml` runs on both `main` and `gh-pages`:

- `main` copies the prebuilt `web/` tree and the workflow to `gh-pages`,
  preserving site-branch history. Its job has no deployment environment.
- `gh-pages` uploads the static branch root and deploys using the existing
  **github-pages** environment. Its branch rule is already satisfied.

The main job uses the automatic `GITHUB_TOKEN` with contents/actions write
permissions. Token-generated pushes do not trigger push workflows, so it
explicitly dispatches the workflow on `gh-pages` after pushing new content.
If the manual publisher already pushed that exact site tree, the main job
leaves it alone and the normal `gh-pages` push runs deployment. Separate
concurrency groups let the staging and deployment runs finish independently.

Pages must already be enabled. The deployment originates from `gh-pages`,
matching both the existing environment policy and the historical source
branch. No environment renaming, new secret or manual branch-policy change
is required. The workflow and publisher do not alter repository settings.

Full builds, algebra checks and profiling run locally before publication;
the deployment workflow uploads already committed assets.

## Static-host isolation

The site includes its own isolation service worker. On a first secure visit,
the entry module registers it in the site directory and reloads once before
starting the app. It adds COOP/COEP to same-origin network responses, enabling
Native NC's shared Wasm workers on Pages without changing repository settings.
It does not store an offline asset cache; GET requests revalidate assets.
Service-worker or isolation failures leave Native disabled and Bergman available.
Both root and project-directory hosting must be checked before publication.
